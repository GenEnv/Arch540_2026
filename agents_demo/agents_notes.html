Part 0

Foundations, told as one story: from a single question to a team of agents. Each chapter adds one part, and each part is something you will see changed in the demos.

0.1

Who decides the next step?

Everything people call "AI" today uses the same kind of model: text goes in, text comes out, once. What differs is what happens around that single step. The clearest way to tell systems apart is one question: who decides what happens next?

A workflow is a system where models and tools follow paths written in advance in code. An agent is a system where the model directs its own process: which tool, how many times, when to stop. Neither is better. A workflow is predictable and cheap; an agent can handle a task whose steps you cannot list in advance, such as "find out why this spreadsheet total is wrong and fix it".

An agent is not a smarter model. It is the same model given a loop, hands, and a way to stop.

0.2

The loop: act, observe, correct, stop

An agent works like someone editing an essay: read it, decide what to change, change it, read it again. The loop is think, act, observe, repeated until the result is good enough or a limit is reached.

A real example from demo A. Asked to write a 150-word statement and check it, the agent wrote a draft, counted it, and its own transcript says: "163 words, over the limit. Revising to trim to 150." Two edits later it counted 149 and stopped. Nobody told it how many rounds to do.

The augmented model

The model at the centre is always the same. What makes it useful is what it is connected to. Each connection is something you choose and set up, and each one appears as a separate step in the demos.

0.3

Patterns: how models and tools are wired together

Before building a team of agents, it helps to know the handful of shapes that almost every system is made of. They were named in an often-cited engineering guide (Anthropic, "Building effective agents", 2024). The first five are workflows: the wiring is fixed. The last is an agent.

The guide's advice is worth repeating: use the simplest shape that works, and add autonomy only when it clearly pays. Demo A is shape 5. Demo B is shape 6 with a skill. Demo D combines 4, 3 and 5.

0.4

Several agents: who talks to whom, and who sees what

An agent can only work with what is in its context (session 2, and 0.7). When one context is not enough, work is split among several agents. A subagent is an agent the main one calls, defined in .claude/agents/<name>.md: a description, which tools it may use, and its instructions. The most important fact about it is that it works in its own context. It does not see the main conversation. It starts from its own instructions, the project files it may read, and the message the main agent writes to it, and it hands back only its final answer.

Why a separate context matters

A reviewer that never heard the writer's reasons judges the result, not the story around it. In demo A, even when the writer's excuse was passed along, the reviewer still flagged the clash with the notes in 6 of 6 reviews. The cost is real: every agent fills its own context, so several agents use many more tokens than one. An often-cited report on a multi-agent research system measured about 15 times the tokens of a chat (Anthropic, 2025), and warns that tasks where every agent needs the same context, or which depend step by step on each other, are a poor fit.

A second use of subagents is simpler: hand off a step. In demo C each family of options is explored by its own helper, and only the helper's best designs come back. In demo D a helper reads the messy task description and lists its constraints before any other work starts.

0.5

The harness: the code around the model

Every box in the last two chapters is a model running inside a harness. The model never runs anything itself. It writes a request, "run this script with these inputs", and stops. A program around it reads the request, checks it is allowed, runs it, and pastes the result back. That program is the harness. Claude Code is a harness.

One tool call, step by step

This is why the transcript matters. When the model says "I checked the rules", the transcript shows whether a check was actually run in step 3. And this is why guards belong in the harness: step 2 happens whatever the model intends.

0.6

Tools, and what the agent can observe

A tool is an action the harness offers: a name, one sentence saying what it does, and the inputs it takes. In Claude Code the everyday tools are read a file, write a file, edit a file, search, and run a command. Writing a small script (a short program) and running it is the most common tool use of all.

What an agent can correct is limited by what it can observe. Give it something that returns countable facts, ask it to run it again after each change, and it will steer by those numbers. In demo A the plain request reported "150 words" three times; the real counts were 160, 147 and 154. A checker can itself be wrong, so test it by hand before you trust it.

0.7

From session 2: context, memory, skills

Three ideas from session 2, briefly, because every demo uses them. The context (context window) is everything the model reads at each step: it can only work with what is in it, and as tool results pile up, early instructions get buried (context rot). Memory is whatever is written down for the next session, most simply CLAUDE.md, read at every start. A skill is a written method; only its one-line description is in the context until it is needed.

0.8

Guards and limits: what code guarantees

Everything so far shapes what the agent tends to do. Some things must happen no matter what it decides: a test before a file is saved, a word limit before it finishes, a stop when the budget is spent. Those belong in the harness, as code.

A hook is a small script listed in .claude/settings.json that Claude Code runs at one of these moments. If a PreToolUse hook exits with code 2, the call is blocked and the hook's message is shown to the model, which then has to react. A Stop hook does the same when the agent tries to finish.

The model saying "I checked" is a promise. A hook is code: it checks exactly what it was written to check, and nothing else. In demo C an agent reached the scoring code by another route and never touched the counter meant to limit it.

0.9

Evaluation: one run is not enough

Before you believe that a change helped, run both versions several times and count what you can see: how many passed the check, how many rounds they took, how many different kinds of design they produced. Four failures are worth looking for in transcripts: claiming a check that never ran, repeating the same fix, forgetting a rule after many rounds, and quietly making the task easier.

# Project statement method

A project statement is read aloud to a review panel that has 30 seconds. Write it like this.

1. First sentence: the one design move, in plain words. What did you do to the building or site? Not the topic, not the programme.
2. One number per claim. Every claim about the project carries one figure from the notes (metres, units, storeys). No number that is not in the notes.
3. No adjective without evidence. "Vibrant", "innovative", "sustainable" are banned unless the next words show the measurable thing behind them.
4. Pick one idea. If the notes hold five ideas, keep the one that explains the others and drop the rest.
5. Facts must agree. If two places in the notes disagree, do not choose silently: say which one you used and flag it to the author.
6. Last sentence: one thing the panel should test or challenge.
7. Stay inside the word limit.

# Site test-fit method

A test-fit is not one drawing. It is a comparison of several organising ideas on the same lot. Work like this.

## 1. Read the rules first
Write down, in two lines each, what the rules do to the scheme before you place anything.
- Low buildings are limited mostly by the 12 m spacing.
- Tall buildings behind each other are limited by the sun gap (0.7 x height of the southern one), so tall and deep rows cost a lot of land.
- The setback and the odd lot outline cut the usable area. Draw the inner (setback) line first.

## 2. Choose an organising logic, then set out its lines
Before placing a building, decide the lines it hangs on (row lines, a court edge, a spine axis, the setback line) and say them in one sentence. Use these strategies. Try all of them; each suits a different reading of the lot.
- **Rows**: parallel slabs, east-west, stacked from the street northwards. Use when the lot is wide. Storeys can step up towards the north so the sun gap stays small.
- **Courtyard**: slabs and short slabs around a central open court, open to the south. Use when you want one strong shared space.
- **Towers on a low base**: one or two low slabs along the street, towers set behind them, staggered so their east-west extents do not overlap. Use when height is worth its sun gap.
- **Spine**: a central open strip running north-south, slabs turned a quarter turn (north-south) on both sides. Use when the lot is deep.
- **Perimeter**: buildings hugging the setback line around the edge, leaving the middle open. Use when the outline is awkward.

2. Launch the constraints subagent. Read its checklist. Every FLAG needs a decision from you: write it in decisions.md (what you decided, why, what a human should confirm). You cannot ask a human in this run, so choose the safest reading and record the assumption in state.json.

4. Launch the analyst on all round-1 scheme ids. Then the reviewer.
5. Round 2 (the last): launch the 4 designers again in one message, each with its own round-1 metrics (copy the failed rules) and the reviewer objections. Analyst on the r2 files, then reviewer again.
6. Choose the final scheme: it must pass all hard rules. Write it in one piece to final/final_scheme.json (a hook checks it). If no scheme passes, write final/NO_VALID_SCHEME.md saying which rules block which schemes. Run: python3 tools/board.py

8. Final answer: at most 15 lines: the final scheme id and its numbers, whether the brief's flags were resolved, disagreements between reviewer and designers, anything that failed.

Which one to use

  • Trying an idea, writing, one page or drawing: Claude chat. Put the brief and references in a Project; add a Skill when you keep repeating the same method.
  • Real work on your own files, and everything in these demos: Claude Code. Everything you can change is a file you can read and edit.
  • A process others will run again and again, where each step must be exactly as designed: LangGraph, or the Agent SDK inside your own program. More setup; complete control.
  • Connecting AI to the office's tools (email, sheets, forms, a schedule): n8n.
  • A chatbot or assistant on your own documents, shared with a team: Dify.

Whatever the tool, ask the same four questions: where does the loop live, what can it observe, what is checked by code rather than by request, and where does it stop.
